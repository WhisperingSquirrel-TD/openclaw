# OpenClaw product/runtime source audit — assigned SkilzVolt skills

**Audit type:** read-only whole-product/runtime-source reconciliation  
**Catalogue revision:** `b95e7feae0186f85306d6000a48ca6c144aeec030d58cfc5e7e171931cb79b12`  
**Catalogue context:** 75 catalogue entries = 70 in scope across the audit set + 5 unique excluded entries  
**Scope:** 18 assigned current, approved SkilzVolt skills in this platform slice  
**Audit outputs:** this report and the machine-readable companion
[`skills-platform-audit.json`](./skills-platform-audit.json)

## Executive result

All 18 assigned names were checked against the live SkilzVolt catalogue at the
catalogue revision above. Every assigned current version matched the live
catalogue. Bodies were fetched with the exact pinned version and continuation
pagination. Two responses carried the returned-data scanner caution:
`app-init` and `transcript-resource` (the latter also on a continuation). They
were not errors or withheld payloads. They were treated as untrusted source
text only; no returned content was executed.

`whatsapp-check` belongs to the operations slice, not this assigned platform
slice; it has no row/card here and is cross-referenced only by the
[operations audit](./skills-operations-audit.md) where needed.

The checkout proves a generic OpenClaw skill-loading and slash-command
framework, a SkilzVolt owner-only adapter, a native YouTube transcript tool,
an OpenAI Whisper shell script, and installer/source snapshots for several Pi
integrations. It does **not** prove that each remote current body is installed,
that a scheduler or service is enabled, that an external credential is valid,
or that a user-facing action completed. Historical audit documents and
`attached_assets/skills` are therefore cited only as source/installer evidence,
never as live current skill truth.

The strongest product result is the native `youtube_transcript` route. The
largest reconciliation risks are:

1. the remote-current skill authority versus local/installer snapshot boundary;
2. Google auth's phone-first contract versus the checked-in poller's SSH-tunnel
   implementation and a referenced helper that is not present;
3. `mgmt-bot`'s “confirm before queueing” rule versus a queue consumer with no
   visible approval field; producer confirmation and an end-to-end approval
   receipt are not proven (the consumer alone does not demonstrate a bypass);
4. the skill-creator SharePoint-manifest gate versus the current skill-update
   contract that explicitly rejects the retired SharePoint library as authority.

No production files, live skills, services, schedulers, secrets, or external
systems were changed. No workflows were restarted and no live invocation was
run. This leaves deployed state, scheduler delivery, and live user activation
unverified by design.

## Confirmed source security finding

### SEC-MGMT-BOT-GITHUB-URL-CREDENTIAL-EXPOSURE — high

This is a **confirmed source vulnerability, not a confirmed live leak**. The
audit read the source only; it did not print a credential, run `git clone`,
invoke the bot, inspect a process, or access a live service.

- `attached_assets/integrations/mgmt-bot/mgmt-bot.py:3026-3029` passes the
  command list to `subprocess.run` without argument redaction.
- At `:3044-3058`, the `git_clone` branch reads `GITHUB_TOKEN`, constructs a
  credential-bearing `auth_url` by inserting the token into the HTTPS URL, and
  passes that URL as an argument to `git clone`. This makes the token
  observable in the child process argv during the clone. Git records the
  supplied origin URL in the destination `.git/config`, and this branch has
  no post-clone remote cleanup. The same token-URL pattern is present in the
  push path at `:3100-3118`.
- The source therefore proves an exposure path to process inspection and
  repository metadata; it does **not** prove that a real token was exposed in
  the deployed runtime.

Remediation is to remove tokens from URLs and argv entirely: use a scoped
Git credential helper or an ephemeral `GIT_ASKPASS`/equivalent protected
credential mechanism with a clean HTTPS remote, clear the helper after the
operation, and redact command/error diagnostics. Add regression tests that
mock subprocess execution and assert the token never appears in clone/push
argv, exercise failure output without credential material, and verify a
temporary clone's `origin` in `.git/config` is credential-free. A static
guard should reject token interpolation into Git URLs. This is a credential
handling repair and does not mandate a second approval gate.
